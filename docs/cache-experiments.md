# Cache experiments: proxy cache and distributed cache

Two synthetic scenarios that demonstrate the simulator extension described in
[distributed-systems-extension.md](distributed-systems-extension.md) (resource-aware service times and affinity
scheduling). They use no real data. The first can be checked against queueing theory, the second shows hard and soft
affinity on a cache cluster.

All files are in `samples/cache_scenarios/`:

| File | Content |
|---|---|
| `proxy_cache/proxycache.bpmn`, `.global.xml`, `.config.xml` | Scenario A, baseline hit ratio 0.8 |
| `distributed_cache/distcache.bpmn`, `.global.xml`, `.config.xml` | Scenario B, variant `hot`, hit ratio 0.9, 2 cache nodes |
| `run_experiments.py` | Generates every variant, runs Scylla, analyses the XES log, prints the tables below |

The `.global.xml` and `.config.xml` files are generated by `run_experiments.py write-samples`; edit the templates in the
script, not the files. The BPMN models are hand-written and can be opened in a BPMN modeller.

## 1. Running the experiments

```bash
# from the project root
mvn -o -DskipTests clean package          # once; builds target/classes and target/libs
cd samples/cache_scenarios
python3 run_experiments.py proxy          # scenario A: hit-ratio sweep against M/D/1 theory
python3 run_experiments.py dist           # scenario B: affinity variants
python3 run_experiments.py exponent       # softmax exponent
python3 run_experiments.py write-samples  # rewrite the committed baseline configs
```

Python 3 (standard library only) and Java are required. Useful options (see `--help` of each command):
`--instances` (requests per run), `--seed`, `--replications` (proxy only, default 5), `--hit`, `--nodes`,
`--variants`, `--warmup` (fraction of requests ignored for waiting times, default 0.1), `--keep DIR` (keep the
generated inputs and the output of every run), `--shared-seeds` (see section 4).

A run of 20,000 requests took under 15 seconds on the development machine (two runs: 16 seconds in total). Each run
happens in a temporary folder, so nothing is written into the repository. The script starts Scylla with
`-Dscylla.quiet=true`, which switches the per-task debug output off.

## 2. Time model and units

- Scylla works in whole seconds and **truncates** fractions of a task duration (the exponent experiment shows 11.89 s
  becoming 11 s). The scenarios therefore use a scaled time axis: **1 simulated second stands for 100 ms of real time**.
  Task durations are tens of seconds, so truncation is a small effect.
- Speeds and demands are abstract units: `cpuSpeed` in instructions per second, `ioRead` in operations per second,
  `txSpeed` in MB per second. Durations follow the model of the extension documentation, `T_cpu = N / (cpuSpeed (1 - idleFactor))`,
  `T_io`, `T_net`, and `T = (T_cpu^p + T_io^p + T_net^p)^(1/p)`.
- Requests arrive with exponentially distributed inter-arrival times (mean 50 s). Resources have no timetable, so they
  are always available.

## 3. Scenario A: proxy cache

### 3.1 Model

```
Request arrives -> Proxy lookup -> [Cache hit?] -- hit  -> Proxy serve hit -> Served from cache
                                                 -- miss -> Origin fetch -> Proxy store -> Served from origin
```

| Task | Resource | Workload | Duration |
|---|---|---|---|
| Proxy lookup, Proxy serve hit, Proxy store | `proxy` (1 node, `cpuSpeed` 1000) | `numInstructions` 2000 | 2 s |
| Origin fetch | `origin` (1 node, `ioRead` 1) | `readOps` 200 | 200 s |

The exclusive gateway sends a request to the hit branch with probability `h` and to the miss branch with `1 - h`. The
hit ratio is an **input**: Scylla has no cache state, so it does not compute the hit ratio, it shows the consequences
of a given one.

### 3.2 Check against theory

Poisson arrivals thinned by the gateway reach the origin at rate $\lambda_{miss} = (1-h)/50$ per second. The origin has
a deterministic service time $S = 200$ s, so it is an M/D/1 queue with

$$\rho = \lambda_{miss}\, S = 4(1-h), \qquad W_q = \frac{\rho\, S}{2(1-\rho)}$$

(The proxy stage is light, about 8% utilisation, so the origin arrival stream is close to Poisson.)

### 3.3 Results

20,000 requests per run, 5 independent runs (seeds 42 to 46) per hit ratio, first 10% of the requests ignored.
"wait origin" is the mean over runs of the mean wait before the origin fetch, ± the standard deviation between runs.
All times in simulated seconds.

Independent random streams (the setting used by the script):

| hit ratio h | ρ origin (sim) | ρ (theory) | wait origin (sim) | W_q (theory) | response, miss | response, hit | realised hit ratio |
|---|---|---|---|---|---|---|---|
| 0.80 | 0.800 | 0.800 | 402.0 ± 26.5 | 400.0 | 606.1 | 4.3 | 0.803 |
| 0.90 | 0.396 | 0.400 | 68.6 ± 6.6 | 66.7 | 272.8 | 4.3 | 0.902 |
| 0.95 | 0.198 | 0.200 | 27.1 ± 2.2 | 25.0 | 231.3 | 4.3 | 0.951 |

The simulated waits agree with M/D/1 theory within the spread between runs, and utilisation matches. The miss response
is consistent with the structure of the process: for h = 0.9, 2 + 200 + 2 s of service plus 66.7 s of origin wait is
270.7 s against 272.8 s simulated (the remainder is waiting at the proxy).

The same hit ratios with Scylla's **default** seeding (`--shared-seeds`):

| hit ratio h | wait origin (sim) | W_q (theory) | deviation |
|---|---|---|---|
| 0.80 | 644.3 ± 42.9 | 400.0 | +61% |
| 0.90 | 99.1 ± 6.5 | 66.7 | +49% |
| 0.95 | 39.5 ± 5.3 | 25.0 | +58% |

Utilisation and the realised hit ratio are unchanged (0.811, 0.399, 0.202; 0.800, 0.901, 0.950), only the waiting times
are biased. The next section explains why.

### 3.4 Why the default seeding biases the result

While validating against theory, the simulated waits came out about 50% too high, reproducibly across seeds and run
lengths (two 50,000-request runs: 100.9 and 101.1 s against 66.7 s). The cause was isolated step by step:

1. **Inputs are correct.** Inter-arrival times have a squared coefficient of variation of 1.03, origin service is exactly
   200 s, and the arrival stream at the origin is close to Poisson (1.10).
2. **The queue is correct.** Requests wait only while the origin is busy, service order is first-in-first-out, and
   queued fetches follow each other with a gap of exactly 0 s. Replaying the same arrival times through an independent
   FIFO queue gives waits that are identical to the simulation for every single request.
3. **The arrival stream is not independent of the gateway.** After a request that misses, the next request arrives on
   average **2.1 s** later, against 54.7 s after a hit (expected for independent streams: about 50 s for both). Misses
   therefore arrive in bursts, which inflates waiting.
4. **Cause.** Scylla seeds every distribution of a configuration with the same value (arrival rate, gateway
   decisions, task durations: `desmojDist.setSeed(randomSeed)`). This is upstream behaviour present in the unmodified
   code. The arrival and gateway streams draw the same random numbers.
5. **Confirmation.** With a separate seed for the gateway the waits were 62.4 s and 72.5 s (two runs) against 66.7 s,
   and the later 5-run experiment gives the table above.

Any Scylla model that combines random arrivals with a gateway is affected in the same way. The default behaviour has
**not** been changed, because that would alter the results of every existing configuration. Instead:

- `-Dscylla.independentSeeds=true` derives a separate seed per exclusive gateway (`randomSeed + 1000003 * nodeId`,
  see `ExclusiveGatewayDistributionConversionPlugin.gatewaySeed`). The default (switch absent) is unchanged. Other
  gateway types (inclusive, boundary events) and task durations still use the shared seed.
- `run_experiments.py` enables the switch; `--shared-seeds` reproduces the default behaviour.

## 4. Scenario B: distributed cache with affinity

### 4.1 Model

```
Request arrives -> Cache lookup -> [Cache hit?] -- hit  -> Return cached value -> Served from cache
                                                -- miss -> DB read -> Cache write -> Cache replicate -> Served from database
```

| Task | Resource | Workload | Duration |
|---|---|---|---|
| Cache lookup | `cache` (N nodes, default 2; `cpuSpeed` 1000, `txSpeed` 1) | `numInstructions` 10000, `txMB` 10 | 10 s CPU + 10 s network, `p = 1` gives 20 s |
| Return cached value | `app` (20 nodes, `cpuSpeed` 1000) | `numInstructions` 2000 | 2 s |
| DB read | `db` (1 node, `ioRead` 1) | `readOps` 200 | 200 s |
| Cache write, Cache replicate | `cache` | `numInstructions` 20000 | 20 s |

Cache nodes are named `#0`, `#1`, ... by Scylla. Arrivals and the gateway are the same as in scenario A.

Three affinity variants (same arrivals and gateway decisions for a given seed, so differences between variants come
only from scheduling):

| Variant | Rules |
|---|---|
| `none` | No rules. The write and the replica go to any free cache node. |
| `owner` | `Cache write`: hard affinity to the node of `Cache lookup` (the key owner). `Cache replicate`: hard anti-affinity to the node of `Cache lookup` (the replica goes to a different node). |
| `hot` | As `owner`, plus a soft affinity (weight 5) of `Cache lookup` to node `#0`, which approximates a hot node. |

### 4.2 Results

20,000 requests per run, 2 cache nodes, softmax exponent 1, first 10% of requests ignored. Hit ratio 0.9 (analytic
database utilisation 0.40). Waits are in simulated seconds; "ρ cache" is the utilisation of node `#0` / `#1`.

Seed 42:

| Variant | wait write | wait replicate | response miss | lookups on #0 | ρ cache #0 / #1 |
|---|---|---|---|---|---|
| none | 0.5 | 0.6 | 321.6 | 0.50 | 0.24 / 0.24 |
| owner | 2.0 | 3.5 | 325.9 | 0.50 | 0.24 / 0.24 |
| hot | 2.7 | 3.4 | 326.4 | 0.73 | 0.33 / 0.15 |

Seed 43 shows the same pattern (miss response 331.5 / 335.8 / 336.2, lookups on `#0` 0.50 / 0.50 / 0.72,
ρ cache 0.24 / 0.24 / 0.33 and 0.15 for `hot`). With hit ratio 0.95 the pattern is the same (seed 42: miss response
285.3 / 289.9 / 290.4, lookups on `#0` 0.50 / 0.50 / 0.74).

Columns that do not depend on the variant (seed 42, h = 0.9): wait for the lookup 0.8 s, wait for the database 59.6 s
(seed 43: 69.7 s, theory 66.7 s), hit response 22.8 s (20 s lookup + 2 s return + 0.8 s wait), database utilisation
0.39.

### 4.3 Interpretation

- **Hard affinity works.** In a 400-request run, all 205 cache writes ran on the node that performed the lookup and
  all 205 replicas on a different node.
- **Pinning has a small, measurable cost.** Compared with `none`, forcing the write and the replica onto specific
  nodes raises their waits from about 0.5 s to about 2 s and 3.5 s, and the miss response by 4.3 s (+1.3%) in both
  seeds. A request must wait for its own node instead of taking any free one.
- **Soft affinity creates imbalance.** The preference for node `#0` moves its share of the lookups from 0.50 to about
  0.73 and its utilisation from 0.24 to 0.33, while node `#1` falls to 0.15. A soft preference only applies while the
  preferred node is free, so the lookup wait does not change (0.8 s in all variants).
- **At this load the latency effect of the imbalance is negligible.** The miss response differs by only 0.5 s between
  `owner` and `hot`, because the database wait (about 60 s) and its 200 s service dominate the response and the cache
  nodes are lightly loaded. The experiments do not show a large latency penalty for affinity; to see one, the cache
  tier would need a much higher load (fewer nodes, shorter inter-arrival times). That has not been run.
- Hit requests are unaffected by affinity (22.8 s in all variants).

## 5. Softmax exponent

`python3 run_experiments.py exponent`: mean service time of `Cache lookup`, which has 10 s of CPU time and 10 s of
network time, for different exponents p (2000 requests per run).

| p | simulated | exact |
|---|---|---|
| 1 | 20.0 | 20.00 |
| 2 | 14.0 | 14.14 |
| 4 | 11.0 | 11.89 |
| 8 | 10.0 | 10.91 |

With two equal components the exact value is $10 \cdot 2^{1/p}$: purely additive at p = 1, approaching the maximum
(10 s) for large p. The simulated values are the exact ones **truncated** to whole seconds (11.89 becomes 11, not 12),
which is how Scylla treats fractions of a second. This is why the scenarios use durations of tens of seconds.

## 6. Verification performed

- Scenario A matches M/D/1 theory for three hit ratios when the random streams are independent (section 3.3); the
  deviation under shared seeds was traced to its cause and confirmed by changing only the gateway seed (section 3.4).
- Scenario B was checked on the event log: every cache write ran on the lookup node and every replica on another node.
- Unit tests: `GatewaySeedTests` (default keeps the shared seed; the switch derives distinct, reproducible seeds per
  gateway), `AffinityRankingTests` and `ResourceCostModelTests` (see the extension documentation).

## 7. Limitations

- The hit ratio is fixed per run. There is no cache state, so hit ratios cannot depend on routing, affinity or cache
  size. Showing such an effect would need a plugin that keeps per-node cache contents.
- Scenario B results come from two seeds per setting and show a single process model; differences of a few tenths of a
  second between variants are within what one should expect from sampling variation. The conclusions above rely on the
  patterns that are identical in both seeds (the 4.3 s cost of pinning, the 0.73 / 0.50 lookup share).
- The default hit-ratio sweep of `proxy` includes 0.7, where the origin is overloaded (ρ = 1.2). Waits then grow
  with the run length and there is no steady state, so this value is not part of the results above.
- The independent-seed switch covers exclusive gateways only (section 3.4).
- Results are in a scaled time unit (1 s = 100 ms) with abstract speeds; they illustrate behaviour and are not
  measurements of a real system.
